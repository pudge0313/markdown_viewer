# 界面排查报告：按钮缺失、正文不能编辑

> 排查时间：2026-11-14　　涉及版本：1.2.0 → 1.2.1
> 结论先说人话，再给代码位置和修改方案。

---

## 0. 三句话结论

1. **按钮确实渲染出来了，但第 5 个「更多」被 Windows 原生窗口按钮盖住了。** 这是真 bug，已在 1.2.1 修掉。
2. **正文不能编辑不是故障，是从没做过。** 这个程序从第一版起定位就是「只读查看器」，代码里没有任何编辑入口，按 Ctrl+S 还会主动提示"不会修改文件"。
3. **"看起来没变化"还有一层原因**：你截的是标题栏那一条，而新功能大多藏在图标点开之后（查找条、侧栏、设置面板），静止时看不出来。

---

## 1. 按钮到底渲染了没有

### 1.1 你截图里的 4 个按钮，逐个对得上

截图宽 1920 物理像素、125% 缩放，对应 1536 CSS px。按像素扫描出的图标位置与代码一一对应：

| 图标中心 x（物理像素） | 图标 | 功能 | HTML 位置 | 逻辑位置 |
|---:|---|---|---|---|
| 1589–1601 | 方框带箭头 | 打开文档 | `src/renderer/index.html:16` | `src/renderer/js/main.js:130` |
| 1627–1640 | 放大镜 | 文档内查找 | `index.html:22` | `src/renderer/js/find.js:136` |
| 1664–1678 | 分栏矩形 | 文件列表 / 大纲 | `index.html:27` | `src/renderer/js/sidebar.js:27` |
| 1702–1716 | 太阳状齿轮 | 阅读设置 | `index.html:32` | `src/renderer/js/settings.js:142` |
| **（应有但整块空白）1740–1776** | **三个点「更多」** | **导出 PDF / 打印 / 快捷键 / 关于** | **`index.html:38`** | **`src/renderer/js/main.js:142`** |

> 也就是说：不是少做了按钮，是它被压在原生按钮底下了。

### 1.2 为什么第 5 个不见了

旧样式把右侧留白**写死**成 115.2px：

```css
/* 修复前 */
#titlebar { padding-right: 115.2px; }
```

而 Windows 原生窗口按钮区在不同系统版本、不同缩放下宽度不同。本次实测（1536px 窗口、125% 缩放）：

```
env(titlebar-area-width) = 1400   →  原生按钮区占 1536 - 1400 = 136 CSS px
```

布局算出来的结果：

| 项目 | 数值（CSS px） |
|---|---:|
| 窗口宽度 | 1536 |
| 代码预留 | 115.2 |
| 按钮组右边缘 | 1420 |
| 原生按钮区起点 | 1400 |
| **重叠** | **20** |

「更多」按钮正好落在 1400–1420 这段被原生按钮不透明底色覆盖的区域里，所以**一个像素都看不到**，也点不到。像素扫描在 1729–1759 区间确实没有任何暗像素。

另一个旁证：我在 1111px 宽的窗口下截图，5 个按钮全都在。所以问题是"窗口一宽 / DPI 一放大就被压住"，不是"没实现"。

### 1.3 修复方式

```css
/* src/renderer/style.css:120-126 */
#titlebar {
  padding-right: max(144px, calc(100vw - env(titlebar-area-x, 0px) - env(titlebar-area-width, 100vw) + 8px));
}
```

原理：`titlebar-area-*` 是系统主动告诉页面的"扣除窗口按钮后还剩多少可用宽度"，比写死像素可靠；浏览器不支持时退回 144px。

**同时要删掉后面重复的 `padding-right: 115.2px`**（原 `style.css:651`）。第一次改完没生效，就是因为这条后面的规则把新规则覆盖了 —— 这也是"改了却没变化"最常见的坑。

验证（修复后，三种窗口宽度）：

| 窗口宽 | 预留 | 按钮右缘 | 原生区起点 | 余量 |
|---:|---:|---:|---:|---:|
| 1536 | 144 | 1391 | 1400 | 9 |
| 1280 | 144 | 1135 | 1144 | 9 |

真机截屏（包含 Windows 原生按钮层，不是网页截图）：

![修复后的标题栏](assets/2026-11-14-titlebar-fixed.png)

5 个按钮齐全，「更多」下拉菜单可以正常展开（打开文件 / 打开文件夹 / 导出 PDF / 打印 / 在资源管理器中显示 / 在新窗口打开 / 设为默认打开程序 / 阅读设置 / 快捷键 / 关于）。

## 2. 正文为什么"不能编辑"

### 2.1 代码事实

| 检查项 | 结果 |
|---|---|
| 全仓库 `contenteditable` | **0 处** |
| 正文节点 | `<article id="view">`（`index.html:95`），只接受 `innerHTML` 渲染结果 |
| 能写文件的 IPC | 只有 `mdv:export-pdf`（`src/ipc.js:210`）写 PDF；**没有保存 Markdown 的通道** |
| 按 Ctrl+S | `src/renderer/js/main.js:122` 主动弹提示：「这是只读查看器，不会修改文件；需要导出请用 文件 → 导出 PDF」 |
| 菜单 | 「文件」只有打开 / 导出 / 打印，没有保存、另存为 |
| README | 「已知限制」明确写了不做编辑 |

### 2.2 结论

**不是功能失效，是这一项从来没在范围内。** 第一版的产品定位就是"只读查看器"，理由是不改动用户文件，就不可能弄坏用户文件；同时避免和已装好的 VS Code / Typora 拼编辑体验。

所以 1.2.0 那次改造补的是**阅读能力**（查找、大纲、公式、图表、代码复制、图片放大、标签页、导出 PDF 等），没有补编辑。

## 4. 想让它"能编辑"，三条路

> **后续（同日）**：已按方案 A 落地，见 [`2026-11-14_编辑能力与界面调整.md`](2026-11-14_编辑能力与界面调整.md)。本节保留为当时的决策记录。


| 方案 | 做法 | 优点 | 缺点 | 工作量 | 风险 |
|---|---|---|---|---|---|
| **A. 源码编辑 + 实时预览**（推荐） | 左边文本框改 Markdown，右边实时渲染 | 行为可预测，不会破坏原格式；复用现有渲染管线 | 不是所见即所得，表格要手写 | 2–3 人日 | 中（写文件需冲突检测） |
| B. 所见即所得 | 正文直接改，反向转回 Markdown | 体验最接近 Typora | 表格/公式/代码块/任务列表容易失真；要么加新依赖，要么维护语法树 | 6–8 人日 | 高 |
| **C. 交给外部编辑器** | 菜单「用系统默认程序打开」，本程序靠现有监听自动刷新 | 半小时能用；零风险；不动"只读"定位 | 编辑体验取决于外部程序 | 0.5 小时 | 极低 |

### 4.1 如果选 A，具体改哪些文件

1. **`src/renderer/index.html`**
   - `#content` 内新增编辑区：`<div id="editor-pane" hidden><textarea id="editor-input" spellcheck="false"></textarea></div>`
   - 顶栏增加「编辑/预览」切换按钮；沿用 `#view` 作为预览区。
2. **`src/renderer/js/editor.js`（新增，约 180 行）**
   - 进入编辑：把 `tab.text` 灌进 `textarea`；
   - 输入：250ms 防抖 → 调用已有的 `renderMarkdown()` → 只刷新预览区；
   - 保存：Ctrl+S → `mdv.saveFile(path, text)`；
   - 离开编辑：提示未保存。
3. **`src/ipc.js`（新增约 30 行）**
   - `ipcMain.handle('mdv:save-file')`；
   - **写前必须过 `safeResolveText`**，并且只允许"当前已打开的文件"；
   - 记录写入前的 `mtime`，若磁盘已被外部改动则返回冲突，交给界面询问覆盖/重载；
   - 原子写：先写 `xxx.tmp` 再 `rename`，避免中途断电把原文件写坏；
   - 保留原文件的 BOM 与换行风格（CRLF/LF），否则 Git 会显示整文件改动。
4. **`src/preload.js`**：暴露 `saveFile(path, text)`，其余不变。
5. **`src/renderer/js/tabs.js`**
   - `tab.dirty` 标记，标签上显示小圆点；
   - 关闭脏标签时二次确认；
   - 保存后忽略自己写入触发的那次 `fs.watch` 事件（比较 `mtime`），否则会重复刷新、光标跳动。
6. **`src/main.js`**
   - 「文件」菜单加「保存」「另存为」；
   - 快捷键：Ctrl+S 保存（当前是拦截后弹"只读"提示，`main.js:120`）。
7. **`src/renderer/style.css`**：左右分栏、编辑区等宽字体、拖拽分隔条、脏标记样式。

### 4.2 如果选 C，改动只有三处

1. `src/ipc.js` 加一个 `mdv:open-in-editor`（内部 `shell.openPath(当前文件)`）；
2. `src/preload.js` 暴露它；
3. `src/main.js` 菜单加「用默认程序打开」。

现有的 `fs.watch` 监听已经能在文件被外部修改后自动刷新（`ipc.js:195`），不需要额外开发。

## 6. 需要你决定的一件事

**要不要做编辑？**

- 如果只是"偶尔想改几个字" → 建议先做 **C**（半小时，零风险）；
- 如果希望在这个程序里正经写文档 → 选 **A**（2–3 人日，我可以直接开工）；
- **B** 不建议：投入最大、最容易把原文件格式弄乱，和当前"绝不弄坏用户文件"的定位冲突。

另外：你截图里跑的是 1.2.0 的包（修复前构建的），换成 `dist/MarkdownViewer-Setup-1.2.1.exe` 才能看到按钮修复；用 `npm start` 的话重启即可。
